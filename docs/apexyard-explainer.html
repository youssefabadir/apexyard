ApexYard v4.3.0 · MIT · multi-project ops framework

Ship AI-built software
like a real engineering team.

ApexYard is a fork-based ops repo that governs a portfolio of projects under a strict SDLC. You don't add it to a project — projects get forged inside it. Claude Code is the default driver, but the rules, hooks, and templates are plain markdown and shell. Swap the AI. Keep the forge.

63 slash-command skills ~30 mechanical shell hooks 23 sub-agents 20 role personas 81 AgDRs 11 CI pipeline templates 3 topology bundles

Proven shipping TypeScript + AWS Lambda backends, Next.js web apps, Chrome extensions, and native Swift macOS desktop apps. The stack is process and guardrails — not a language or framework lock-in.

The problem it solves

Claude Code is powerful, but without structure it produces inconsistent results. Every team reinvents the same processes — role definitions, review checklists, document templates, workflow gates. ApexYard provides that structure as a reusable, open-source stack: one config file to customise, 20 role definitions to use, battle-tested workflows to follow, and ~30 shell hooks that enforce the rules mechanically.

Who it's for

Founders who ship alone, or companies standing up AI-enabled squads. If you're tired of re-explaining your SDLC to the model every session, and tired of merges you can't audit, ApexYard is built for you.

Mental model — one ops repo, many projects

You fork me2resh/apexyard into your org. The fork is your ops repo. A single registry file at its root lists every project under management. Per-project docs live in projects/<name>/; optional live working copies live in workspace/<name>/ (gitignored). Skills like /projects, /inbox, /status, /tasks aggregate across the registry — even if you only have one repo.

workspace/<name>/

Live working copies — gitignored

Real git clones of your managed projects. Branches, PRs, and CI happen here. Gitignored in your fork because each project has its own remote.

projects/<name>/

ApexYard docs per project — committed

Roadmaps, handover assessments, stakeholder updates, architecture diagrams. Committed to your fork (or your private sibling repo) alongside the registry.

The "where does this doc go?" test

Would I want this to follow the code if the project was spun out tomorrow? If yes → put it in the project's own repo (workspace/<name>/docs/). If no → put it in projects/<name>/ in your fork.

The trip-wire

GitHub Free disallows changing a fork's visibility — you can't make a fork of a public repo private after the fact. If you have any private project and you're on the free tier, start in split-portfolio mode. The /split-portfolio skill automates the migration if you've already pushed private names to a public fork.

The 5-layer .claude/ architecture

ApexYard ships a .claude/ directory that turns the markdown content into a runnable workflow. Claude Code picks it up automatically when the directory lives at the project root. Five layers, each loaded differently, each enforced differently.

Skills
63 slash commands

One SKILL.md per subdirectory. Each is a markdown runbook the agent drives in-thread when you type /<name>. Examples: /setup, /handover, /start-ticket, /approve-merge, /release.

loaded by slash command, invoked by user or model
Hooks
~30 shell scripts

Wired to PreToolUse, PostToolUse, SessionStart, and UserPromptSubmit events in settings.json. Each returns exit 0 (allow) or exit 2 (block with a BLOCKED: ... message + unblock recipe).

exit 0 allow   exit 2 block
Agents
23 sub-agents

Markdown persona wrappers spawned via the Agent tool. Own the model tier (opus/sonnet/haiku) and tool allow/deny list per role. Rex (code-reviewer), Hakim (security), Tariq (solution architect), Munir (deps), Idris (tickets), Naqid (contrarian).

isolated-work-class spawn sub-agent   in-flow-class adopt in-thread
Rules
12 markdown files

Plain markdown imported into CLAUDE.md via the @.claude/rules/* directive. Advisory by default; backed by a matching hook where one exists. Examples: workflow-gates.md, role-triggers.md, pr-workflow.md.

imported @.claude/rules/<name>.md
Session
gitignored runtime state

Per-machine markers at .claude/session/: active tickets, review approvals, bootstrap-skill flag. Written by skills + agents, read by hooks. Never committed. This is the mechanical substrate the gates read/write to.

tickets/ reviews/ active-bootstrap
Why shell hooks matter

Rules in markdown are advisory — the model can drift. Hooks are mechanical: a script returning exit 2 blocks the tool call before it happens, no matter what the model "decided". The framework's design principle is fail-open on tooling, fail-closed on policy: a missing jq degrades gracefully; a missing ticket marker hard-blocks the edit.

The full session-state surface

Every marker file the framework reads or writes under .claude/session/:

.claude/session/
tickets/<project>                        # Tier 1 per-project marker (a FILE)
tickets/<project>/<safe-branch>           # Tier 0 per-worktree marker (parallel agents)
current-ticket                            # Tier 2 ops-fallback marker (framework edits)
active-bootstrap                          # one-line marker naming the running bootstrap skill
active-issue-skill                        # marker for the active issue-filing skill
reviews/<owner>__<repo>__<pr>-rex.approved  # bare-SHA marker written by Rex on APPROVED
reviews/<owner>__<repo>__<pr>-ceo.approved   # structured marker written ONLY by /approve-merge
reviews/<pr>-architecture.approved          # Solution Architect sign-off (Tariq)

All review markers are repo-qualified as of AgDR-0060 so the same PR number in two repos never collides.

You don't need a CLI to use ApexYard

The framework's primary UX is slash-commands inside Claude Code. The shell CLI is intentionally tiny — one command today, apexyard status, delegating to .claude/skills/status/briefing.sh. Install it with ln -s "$(pwd)/bin/apexyard" ~/.local/bin/apexyard if you want a quick "where am I" outside Claude Code.

The SDLC it enforces

Every feature moves through seven phases. Each phase has entry criteria, activities, exit criteria, and a quality gate. The gates are not suggestions — they're enforced by hooks that return exit 2 on violation.

1Planning
2Design
3Build
4Review
5QA
6Deploy
7Monitor

The six gates

GateBeforeVerifyEnforced by
1PRD → Tech DesignPRD approved, parent epic existsadvisory
2Tech Design → BuildDesign approved, story tickets exist, AgDR for key decisionsadvisory
3Starting codeTicket exists, branch created, design review if UI workrequire-active-ticket.sh
3aStarting a migration editActive ticket has migration label + body references a migration AgDRrequire-migration-ticket.sh
3bDesign → Build (merging a design-artifact PR)Solution Architect (Tariq) sign-off marker at matching HEAD SHArequire-architecture-review.sh
4Creating PRTests pass, checks pass, >80% coverage, AgDR linked if decisions madevalidate-pr-create.sh, require-agdr-for-arch-pr.sh
5Merging PR2 reviews (Rex + CEO per-PR), CI green, SHA matches reviewblock-unreviewed-merge.sh, block-merge-on-red-ci.sh
6Ticket → DoneQA verified, signed offadvisory (label-based)
If a gate fails → STOP

Complete the missing step first. There is no override flag. The escape hatches are explicit and audited: <!-- multi-close: approved --> for release PRs that legitimately bundle many tickets; <!-- agdr: not-applicable --> for diffs the AgDR gate misfires on; <!-- pre-push: skip --> for a one-off emergency push.

One ticket at a time — the load-bearing rule

Work on ONE ticket at a time. Complete it fully before starting the next. Each PR = one ticket only.

WRONG
Start #6 → Start #7 → Start #8
        → PR with all 3
RIGHT
Start #6 → PR → Review → QA → Done
Start #7 → PR → Review → QA → Done
Start #8 → PR → Review → QA → Done

The framework draws a sharp line between throwaway learning and the production spine:

One ticket, one PR, the full SDLC. This is what the framework actually does at each phase, with the real skill invocations, the real hook firings, and the real session-state writes.

Phase 1 — Planning

The product manager (Mariam) drafted the PRD via /write-spec. The Tech Lead (Hisham) reviews it and breaks it into story tickets. The Pre-Build gate is satisfied because the parent epic + user stories + ACs all exist in GitHub Issues.

Phase 2 — Technical Design

Hisham authors the technical design. Before drafting, he runs /agdr search export to check whether the portfolio has already decided on a CSV library. (It has — AgDR-0042 picked papaparse for a sibling project; he reuses it.) The design lands as a PR. Before it can merge, the architecture gate fires:

Phase 4 — Code Review

You push the branch and open a PR. The branch-name hook fires on git push; the PR-create hook fires on gh pr create. Then automatically, the auto-code-review.sh PostToolUse hook triggers Rex on the new PR.

bash

gh pr create --title "feat(#42): add CSV export" --body-file pr-body.md

Rex (the code-reviewer agent, model: opus) reviews the diff, consults the framework rules + adopter handbooks, and on APPROVED writes the local approval marker and posts a GitHub review:

Phase 5 — Merge (the two-marker gate)

You cannot merge yet. Plan-level "go" is explicitly not merge approval. You ask the CEO explicitly: "PR #42 ready to merge — approved?" On "approved", you run:

/approve-merge 42

The skill writes the structured CEO marker (the merge gate rejects the old bare-SHA format):

skill_version=2
approval_summary=CEO per-PR approval for #42 CSV export

Then gh pr merge 42 --squash --delete-branch goes through. The merge gate reads both markers and verifies both SHAs match HEAD.

The 5-dimension harnessability score

When you run /handover, the skill scores the target repo across five dimensions: type safety, module boundaries, framework opinionation, test coverage signal, lint baseline. A "low" score warns verbatim that Rex's blocking handbooks will false-positive — so you know to either tighten the codebase or relax the handbooks before the first review.

Hooks — the mechanical gates

Hooks are the load-bearing layer. A rule in markdown is a suggestion; a shell script returning exit 2 is a wall. Every hook emits a BLOCKED: ... message to stderr that names the missing artefact and gives a concrete unblock recipe.

The exit-code contract

exit 0

Allow

The tool call proceeds. Advisory hooks (warnings, drift banners, MCP suggestions) also use 0.

exit 2

Block

The tool call is cancelled. stderr begins with BLOCKED: and ends with a "To unblock" guide. The model sees it and can self-correct.

fail-open

Tooling missing

If a required tool (jq, shellcheck, npx) is missing, the hook skips with exit 0 and an install hint — never hard-blocks a contributor for a missing binary.

The real BLOCKED message from validate-branch-name.sh
stderr — after pushing a branch named "add-export"
BLOCKED: Branch 'add-export' doesn't follow naming convention.

Required shape (.claude/rules/git-conventions.md § "Branch Naming"):
  {type}/{TICKET-ID}-{description}

Accepted types: feature, fix, refactor, chore, docs, test, spike, ci, build, perf, sync
  (configurable: .claude/project-config.*.json → .branch.type_whitelist)

Accepted ticket-ID pattern: (#?[0-9]+|[A-Z]{2,10}-[0-9]+)
  (configurable: .claude/project-config.*.json → .tracker.id_pattern)

Examples:
  feature/ABC-123-add-auth
  fix/GH-45-login-bug
  docs/ENG-99-update-readme

To unblock:
  1. Pick a ticket-ID (existing or new): /feature, /task, /bug
  2. Pick a short kebab-case description (max ~40 chars)
  3. Rename the current branch in place:

Why exit 2 with a recipe, not a silent fail

The model sees the stderr. A well-written BLOCKED: message tells the model exactly what to do next — file the ticket, invoke the skill, fix the format — so it self-corrects in the next turn instead of flailing. This is the framework's feedback loop: hooks teach the model by blocking, not by erroring.

The real migration-safety.md BLOCKING handbook (excerpt)
handbooks/architecture/migration-safety.md
ENFORCEMENT: blocking

# Handbook: Migration Safety

**Scope:** all PRs (handbook lives under architecture/ — Rex always loads it).
**Enforcement:** blocking — Rex requests changes if it detects a violation.

## The rule
Database schema migrations must be backwards-compatible for at least one
release. A single migration MUST NOT do any of:
- DROP COLUMN/TABLE on what the previous release reads/writes
  (rolling-deploy crash window)
- RENAME COLUMN/TABLE in a single step
  (add copy → dual-write → drop, across releases)
- ALTER COLUMN to more restrictive type/NOT NULL without a default
- Drop/narrow an enum value the old code might emit
- Reorder or change semantics without a feature flag

## Why
Production rollouts are not atomic. During a deploy window (30s–30min)
both old and new code run against the same database. The "backwards-
compatible for one release" rule converts every breaking change into a
planned two-step over two releases. This pattern is slow on purpose.
The slowness is the safety.

## Sample finding
> ⛔ Migration safety — BLOCKING
> prisma/migrations/.../migration.sql drops users.role_v1. The previous
> release still reads this column in src/auth/role-resolver.ts:42. A
> rolling deploy crashes old instances on every login request during
> the window.
> Required fix: split into two PRs across two releases: this release
> stop reading role_v1; next release drop the column.

## What's NOT a violation
- Adding (additive) columns/tables/enum values
- DROP on a column added+deprecated in a prior release
- Pure data backfills with no schema change

## Override
Intentional violations must link a migration AgDR documenting the
breaking change, why BW-compat is skipped, downtime/rollback plan,
cross-service consumer list. With AgDR linked, Rex marks this check
N/A — the AgDR is the audit trail.

The best way to use it

Concrete patterns drawn from the rule files, AgDRs, and the operational wisdom baked into the skills. These are the do/don't that separate a smooth ApexYard experience from fighting the gates.

Do — the patterns that pay off

1. Use /setup, don't hand-edit onboarding.yaml

The skill is a 3-exchange interview that produces a consistent config, refuses to run without jq, offers the LSP install for your detected language, and writes the .apexyard-fork marker. Hand-editing misses the marker, the LSP offer, and the registry seeding. Run /setup --reset to re-run cleanly.

2. One ticket at a time — it's not a style preference, it's a gate

The require-active-ticket.sh hook writes a per-project marker when you run /start-ticket. If you start #6, then #7, then #8, the marker for #6 gets overwritten — and your PR (which the validate-pr-create.sh hook will refuse if it bundles multiple Closes #N lines without the escape marker) won't merge. The RIGHT pattern is the loop in the SDLC section above: Start → PR → Review → QA → Done, one ticket at a time.

3. Get the AgDR before the architecture lands

Run /agdr search <term> before drafting a design. If a prior AgDR covers your decision, reuse it — the require-agdr-for-arch-pr.sh hook will block your PR if you introduce a new pattern without linking one. If you're genuinely deciding something new, run /decide during the design phase, not after. The AgDR is the audit trail; writing it post-hoc during PR review is already too late.

4. Pick the right early-work scaffold

If you're asking…UseWhy
"Will this technically work?"/spikeThrowaway; exempt from AgDR + 80% coverage. /spike-close --promote or --discard when answered.
"What should it look and feel like?"/prototypeThrowaway UX/demo. Same exemptions as /spike.
"Is the whole architecture wired end-to-end?"/walking-skeletonKEPT. Full SDLC, no exemptions. You grow the product on top of it.
"This bug resisted the obvious fix."/bug → /debugForces architecture-first reading + evidence-before-fix. Don't use /debug for simple bugs — the ceremony exceeds the fix cost.
"Multi-session mystery / regression hunt."/investigationLive-doc workflow; cross-session continuity.

Don't accidentally promote a throwaway into production — that confusion is exactly what the taxonomy exists to prevent.

5. Use split-portfolio mode if you're on GitHub Free with any private project

GitHub Free disallows changing a fork's visibility. If you start in single-fork mode and push private project names to your public fork, the /split-portfolio skill automates the destructive recovery flow (force-push main to remove the registry from history, redact Issue/PR bodies, move data to a private sibling repo). It's gated at every step but it's still destructive. Start in split-portfolio mode if you have anything private.

6. Pull opusplan as the cost lever

In-flow roles run on your primary tier (usually Opus) — that's why the main agent dominates token spend. The biggest cost win, with no framework change, is opusplan: Opus plans, Sonnet executes. Second lever: the thin-orchestrator pattern — keep the Opus loop as a planner/coordinator and delegate implementation to spawned sonnet build agents via /fan-out or Workflow. Third: populate agent-routing.yaml to pin per-agent tiers. See docs/orchestrator-cost-model.md.

7. Get the per-PR CEO approval, not the plan-level "go"

The merge gate rejects plan-level approval. Even after the CEO says "go" on a multi-step plan that includes a merge step, you MUST first execute the non-merge steps, then ask "PR #X ready to merge — approved?", get "approved", THEN invoke /approve-merge X. The block-unreviewed-merge.sh hook checks for a structured CEO marker with approved_by=user and skill_version >= 2 — bare-SHA legacy markers are rejected.

8. Let /handover score your repo before the first review

If the 5-dimension harnessability score comes back "low" on test coverage or lint baseline, Rex's blocking handbooks (especially migration-safety.md) will false-positive. Either tighten the codebase first, or relax the offending handbook to advisory (ENFORCEMENT: blocking → remove the line) before the first review. The score is a forecast; use it.

Don't — the patterns that bite

1. Don't cargo-cult the dev/main split into managed projects

The release-cut branch model (dev daily trunk, main release-only) is framework-only. Managed projects under ApexYard governance stay trunk-based — PRs merge to main directly because they have no downstream consumers. The /release skill is the only piece that's framework-specific and refuses to run on a managed project. Don't push the dev/main split into project templates, scaffolds, or /handover output.

2. Don't git add -A / git add .

The block-git-add-all.sh hook hard-blocks both. Staging must be explicit — stage specific files. This is the leak-protection backstop: it prevents a filled-in onboarding.yaml or a stray .env from riding along in a git add -A.

3. Don't auto-close tickets with Closes #N when QA verification is required

When a merged PR needs QA verification, use Refs #42 + the qa label, NOT Closes #42. The QA gate is mandatory — a merged PR is never Done until Salim has verified every acceptance criterion. Auto-closing via Closes #XX is intentionally overridden.

4. Don't hand-merge upstream/main

Run /update. It's a 10-step flow (see Upgrading for the full breakdown): preview, sync branch, merge/rebase, conflict resolution, deprecated-config detection, split-portfolio v1→v2 offer, the per-version migration chain, topology drift — then leaves a branch ready to push. Hand-merging skips the migration chain (shipped since v1.4.0) and you'll discover the breakage mid-skill. And don't reach for --from-dev casually — it's hidden on purpose; the adopter contract is tagged releases.

5. Don't push to main or dev directly

block-main-push.sh blocks it. Every change goes through a PR. This applies to the framework fork (dev + main) AND to managed projects (main). The only exceptions are release PRs (framework) and the narrow branch-name allowlist (release/v*, sync/main-to-dev-after-*).

Upgrading & community

Keeping your fork current

Run /update. It's the single-command replacement for the manual "fetch → branch → merge → push → PR" dance. It previews the upstream diff, merges on a sync branch (never directly on main — block-main-push.sh blocks that), handles conflicts one file at a time, detects deprecated config keys, offers the split-portfolio v1→v2 migration, walks the per-version migration chain, checks topology drift, and leaves a sync branch ready to push. A SessionStart drift banner tells you when a new tag is available — you won't forget for 6 months.

terminal
/update                              # merge-based sync (default, safer)
/update --rebase                     # rebase local customisations on top of upstream
/update --dry-run                    # preview only, don't touch anything
/update --from-version v1.2.0         # override the version anchor (when missing/stale)
/update --skip-migrations            # files-only sync; skip the per-version chain
/update --from-dev                   # (hidden) pull from upstream/dev — pre-release; expect breakage
--from-dev is hidden on purpose

The adopter contract is tagged releases from upstream/main (release-cut model, AgDR-0007). --from-dev pulls pre-release work and is deliberately omitted from the skill's description frontmatter so /help doesn't surface it — it IS in ## Usage and ## Options for operators who read the spec. When used, it prints a ⚠ PRE-RELEASE SYNC banner BEFORE any git fetch so the deal is restated every invocation, and the migration chain auto-skips (pre-release has no tag to anchor against). Use cases: the framework maintainer testing pre-release work on another machine; adopters validating an upcoming change before the wider rollout.

The skill never runs Rex or /approve-merge automatically — the sync branch is "ready to push", and the operator owns the PR + merge approval like any other change.

The per-version migration chain (step 8b) — real example

When an adopter jumps multiple releases at once (e.g. v1.0.0 → v1.4.0), the chain walker reads .claude/framework-version (the version anchor), compares against the latest upstream tag, builds the ordered list of pairs, and offers each migration with a [Y / n / show-diff / skip-all] prompt. Design rationale: AgDR-0032.

Why a file anchor, not a derived signal

The version anchor is a standalone one-line file .claude/framework-version, not a key in project-config.json and not derived from the last merge-from-upstream commit. Derived signals are fragile under squash-merge and rebase; mixing a measured fact into configured facts invites drift on copy/paste. /update owns the file.

Split-portfolio v1→v2 auto-migration (step 8a) — what it moves

If /update detects a pre-v2 split-portfolio fork (has a portfolio: block but no .apexyard-fork marker), it offers the migration. Per AgDR-0021 § H: onboarding.yaml is COPIED (small file, snapshot kept as legacy fallback); workspace/ is MOVED (gigabytes, no duplication).

  - apexyard.projects.yaml     → resolved to a sibling private repo (good)
  - projects/                  → resolved to a sibling private repo (good)

Migrate now? This will:
  - COPY onboarding.yaml to the sibling private repo (sibling becomes canonical)
  - MOVE workspace/<name>/ contents to the sibling private repo

  - Write a .apexyard-fork marker (the v2 ops-fork anchor)
  - Add portfolio.{onboarding,workspace_dir} keys to .claude/project-config.json

[Y / n / dry-run — show commands, don't execute]

Per-file-class confirmation — you can migrate onboarding.yaml and defer workspace/. Idempotent — re-running on a v2 layout is a no-op. The skill never commits — staging is the contract; you own both the public-fork commit AND the sibling-repo commit.

The re-fork escape hatch

If your fork has drifted too far to merge cleanly, re-fork and keep your data: in split-portfolio mode your registry, per-project docs, onboarding config, and workspace clones all live in the private sibling repo. Re-fork the public framework, point the portfolio: config block at the same sibling, and you're back. Single-fork adopters can /split-portfolio first to get to that safe state.

Contributing to the framework itself
